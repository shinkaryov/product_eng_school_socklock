# UA Insight

Локальна утиліта для зіставлення рекламних витрат із результатами продажів, аналізу ефективності та формування черги перевірок. Приймає два експорти, нормалізує їх, перевіряє якість даних і створює HTML-звіт з графіками, таблицею та поясненнями.

Python 3.10+. Сторонні бібліотеки, сервер, доступ до рекламних кабінетів та інтернет не потрібні. Згенерований HTML відкривається подвійним кліком й працює офлайн. Обчислення не використовують LLM.

## Запуск

Розпакуйте архів і відкрийте термінал у папці `ua_insight`:

```bash
python3 ua_report.py --ads demo/ads.csv --analytics demo/analytics.json --start 2026-10-26 --end 2026-11-01 --as-of 2026-11-05 --out output
```

Відкрийте `output/report.html`. На Windows використовуйте `py` замість `python3`.

Готовий демонстраційний звіт: `demo_output/report.html`. Усі дані `demo/` синтетичні. Демо охоплює два послідовні семиденні періоди, дві валюти, прибуткові/збиткові оголошення, падіння ефективності та розрив між джерелами.

Приклад із заголовками рекламного експорту, десятковою комою та JSONL-аналітикою:

```bash
python3 ua_report.py --ads demo/ads_meta.csv --analytics demo/analytics.jsonl --config config.example.json --start 2026-10-26 --end 2026-11-01 --as-of 2026-11-05 --out output
```

Дати включні. `--as-of` — дата, станом на яку оцінюємо зрілість атрибуції. Попередній період визначається автоматично: стільки ж календарних днів безпосередньо перед `--start`. Додайте дані обох періодів до експорту. Без базового періоду поточні KPI доступні, але тренди позначені як недоступні.

## Формати входу

| Формат | Структура |
|---|---|
| CSV | UTF-8 або UTF-8 BOM; кома, крапка з комою або табуляція визначається автоматично |
| TSV | UTF-8, табуляція |
| JSON | Масив об’єктів з однаковим набором ключів |
| JSONL / NDJSON | Один об’єкт на рядок, однакова схема |

Формати двох джерел можуть відрізнятися. XLSX, Parquet і сирі події покупок не підтримуються. За потреби експортуйте таблицю в один із форматів вище. Ліміти: 50 MiB та 250 000 рядків на файл, період аналізу — до 366 днів. Усі записи зберігаються в пам’яті.

Обов’язкові спільні поля: `date, ad_id, country, currency`.

Рекламні поля: `spend, impressions, clicks`.

Аналітичні поля: `purchases, net_revenue, variable_costs`.

```csv
date,ad_id,country,currency,spend,impressions,clicks
2026-10-26,ad_001,US,USD,100,10000,200
```

```json
[{"date":"2026-10-26","ad_id":"ad_001","country":"US","currency":"USD","purchases":20,"net_revenue":400,"variable_costs":80}]
```

Один рядок — одне оголошення за один день, країну та валюту. `net_revenue` має бути виторгом після повернень, знижок і непрямих податків. `variable_costs` включає витрати на ці покупки без рекламного бюджету. Використовуйте однакові часовий пояс, модель атрибуції та її вікно в обох джерелах. Ключі не перевіряють цю семантичну сумісність автоматично.

Для днів без покупок додавайте явні нулі. Відсутній рядок означає невідомий результат. Якщо оголошення було неактивне й це відомо, додавайте узгоджені нульові рядки в обидва джерела. За відсутності незалежного реєстру активності утиліта не відрізняє пропущений день від неактивного чи нового оголошення.

## Нормалізація колонок

Поширені назви визначаються автоматично, без чутливості до регістру та з нормалізацією пробілів/підкреслень:

| Канонічне поле | Приклади альтернатив |
|---|---|
| date | Day, Reporting starts, дата |
| ad_id | Ad ID, advertisement_id |
| country | country_code, країна |
| currency | currency_code, валюта |
| spend | Amount spent, Amount spent (USD), cost, витрати |
| impressions | покази |
| clicks | Link clicks, кліки |
| purchases | orders, purchase_count, покупки |
| net_revenue | net_sales, net revenue, чистий виторг |
| variable_costs | cogs_and_fees, variable costs, змінні витрати |

Загальне поле `revenue` навмисно не вважається чистим виторгом. Перш ніж явно зіставити його з `net_revenue`, перевірте значення. `clicks` та `link clicks` також повинні мати узгоджений зміст для порівнянь.

Нестандартне зіставлення задається як **канонічна назва → точний заголовок джерела**:

```json
{
  "inputs": {
    "ads": {
      "columns": {"spend": "Media cost", "ad_id": "Creative identifier"},
      "decimal_separator": ",",
      "date_format": "%d/%m/%Y"
    },
    "analytics": {
      "columns": {"net_revenue": "Revenue after refunds"}
    }
  }
}
```

Не вгадуємо `01/02/2026`: для не-ISO дат задайте формат. Десятковий роздільник за замовчуванням — крапка. Для `1234,50` вкажіть `","`. Пробіли в числах дозволені, роздільники тисяч комою/крапкою — ні. JSON-числа вже типізовані та не залежать від десяткової локалі. Довгі ID передавайте текстом; числові JSON ID понад 2^53−1 відхиляються, щоб уникнути втрати точності в сторонніх системах.

## Захисні перевірки

Обробка завершується кодом 2 з поясненням файлу/запису за таких умов:

- Відсутні або неоднозначні колонки, дублікати заголовків/JSON-ключів, різні схеми записів.
- Повторюється ключ `(date, ad_id, country, currency)`. Розрізи за пристроями чи плейсментами потрібно агрегувати явно.
- Порожні ключі, керувальні символи, надто довгі ID, невалідні дати, дати після `as-of`.
- NaN, Infinity, null, boolean, від’ємні значення, дробові лічильники, числа понад 1e12 або понад 6 десяткових знаків.
- Кліків більше за покази, витрати є без показів, виторг/витрати на покупки є при нульових покупках.
- Заголовок Amount spent (USD) конфліктує з валютою рядка.
- Відоме поле кінця звітного періоду показує, що рядок агрегований за кілька днів.

Неузгоджені джерела не зупиняють весь звіт: група отримує `DATA_ISSUE`, фінансові KPI приховуються, а непарні записи потрапляють у `issues.csv`. Доступні spend та кількість покупок у такій групі — лише часткові суми для діагностики, не узгоджений результат.

Покупок більше за кліки — окремий `ATTRIBUTION_REVIEW`: це можливо за view-through або повторних покупок, тому не є автоматичною помилкою, але блокує kill/scale. Пропущені дні створюють попередження та за стандартних порогів блокують рішення. Покриття рахується від повної довжини календарного вікна.

Неправильні дані не відкидаються мовчки. Суворі правила для повернень і нульових покупок передбачають денну когортну модель; окремі коригування чи облікові витрати потрібно підготувати до імпорту.

## KPI

```text
gross_profit = net_revenue − variable_costs
EGP = gross_profit − spend
ROMI (%) = EGP / spend × 100
ROAS = net_revenue / spend
CPA = spend / purchases
CTR (%) = clicks / impressions × 100
CVR (%) = purchases / clicks × 100
CPC = spend / clicks
CPM = spend / impressions × 1000
AOV = net_revenue / purchases
```

У цій моделі EGP — внесок після змінних витрат і реклами, без постійних витрат та прогнозу LTV. ROMI беззбитковості = 0%. Якщо у вашій організації ROMI визначений інакше, узгодьте формулу до використання порогів.

При діленні на нуль повертається пропуск. Python-розрахунки використовують Decimal. HTML використовує звичайні числа JavaScript для відображення графіків і підсумків; точні значення Python доступні у CSV. ROMI підсумку рахується від сум, а не як середнє відсотків.

## Автоматичні висновки

Сигнали обчислюються автоматично, фінальне рекламне рішення залишається за менеджером.

1. Перевірка якості даних і зрілості атрибуції.
2. Перевірка мінімальних витрат, кількості днів і покриття періоду.
3. Визначення KILL_REVIEW, SCALE_REVIEW, HOLD або WAIT.
4. Порівняння з попереднім рівним періодом: ROMI у процентних пунктах, CPA/CTR/CVR/CPM/AOV/spend — відносна зміна у відсотках. База доступна лише за достатнього покриття обох періодів, повних фінансових даних і мінімального spend у кожному.
5. Суттєве падіння ROMI змінює HOLD або SCALE_REVIEW на DECLINE_REVIEW. Якість/зрілість мають вищий пріоритет.
6. Падіння CTR/CVR або зростання CPM на 20% дають діагностичні підказки за достатніх показів/кліків у двох періодах. Це спостереження, а не встановлена причина чи статистично значущий результат.
7. Черга сортується: проблеми даних → атрибуція → збитки → погіршення → масштабування → очікування → утримання. Усередині категорії KILL — за спостережуваним збитком, решта — за охопленим spend. Суми не трактуються як гарантована економія.

| Налаштування | Стандартне значення |
|---|---:|
| min_spend | 100 одиниць валюти |
| min_purchases | 10 для масштабування |
| kill_romi | 0%: кандидат, якщо ROMI строго нижчий |
| scale_romi | 25%: кандидат, якщо ROMI не нижчий |
| maturity_days | 3 календарні дні |
| min_days | 3 зіставлені дні |
| min_impressions | 1 000 |
| min_clicks | 30 |
| min_coverage | 1.0: повний поточний період |
| trend_drop_pp | 20 п.п. |

`analysis.thresholds` задає перші п’ять порогів. `analysis.currencies` перевизначає їх для окремих валют, наприклад `{"CZK":{"min_spend":2500}}`. Решта параметрів задаються безпосередньо в `analysis`. Повний приклад — `config.example.json`. Це налаштовувані евристики, не результати статистичного тесту.

Незрілий день у поточному вікні блокує kill/scale всієї відповідної групи. Для аналізу лише зрілих даних скоротіть `--end`. Незрілі повні групи можуть входити у KPI та графіки як спостережені значення.

## HTML-звіт

- Компактний перемикач валюти змінює всі підсумки, графіки, висновки, таблицю та проблеми. Валюти не підсумовуються й не конвертуються.
- Верхні показники — spend, EGP, ROMI та покупки для повних поточних груп.
- Графік spend/EGP показує два періоди для когорти повних поточних груп. День з неповною когортною базою має розрив, а не нуль.
- Горизонтальні стовпці показують до 10 груп із найбільшим абсолютним EGP.
- Черга перевірок містить факти, порівняння, діагностичну гіпотезу та наступну дію.
- Таблиця підтримує пошук ID/країни, фільтр статусу, сортування й експорт відфільтрованих рядків. Фільтри таблиці не змінюють загальні KPI/графіки.

Звіт не завантажує зовнішніх скриптів, шрифтів чи даних. Дані безпечно вставляються в HTML, а текстові CSV-поля захищені від інтерпретації як формул.

## Вихідні файли

| Файл | Вміст |
|---|---|
| report.html | Інтерактивний офлайн-звіт |
| report.csv | Повний список KPI, сигналів і пояснень |
| report.json | Дані звіту для подальшої обробки |
| daily.csv | Денна когортна статистика; matched_groups та expected_groups показують повноту |
| issues.csv | Непарні записи та попередження про покриття |
| audit.json | Періоди, параметри, зіставлення колонок, кількість записів і SHA-256 вхідних файлів |

У `daily.csv` суми при неповному matched_groups є частковими; HTML їх не з’єднує в лінію. Повторний успішний запуск перезаписує результати в `--out`. За помилки валідації новий звіт не створюється; старі файли в цій папці можуть лишитися, тому перевіряйте код завершення та параметри audit.json або використовуйте окремі папки запусків.

## Структура та тести

- `ingest.py` — читання, визначення колонок, нормалізація та валідація.
- `core.py` — Decimal-арифметика, full outer join і базові правила.
- `insights.py` — покриття, порівняння періодів, діагностика та пріоритети.
- `report.py`, `template.html` — експорт та самодостатній HTML.
- `ua_report.py` — CLI та аудит джерел.
- `generate_demo.py` — відтворювані синтетичні експорти.

```bash
python3 -m unittest discover -s tests -v
python3 generate_demo.py
```

Тести охоплюють формати, локалі, неоднозначність схеми, погані дані, фінансові формули, пропуски, зрілість, тренди, валютні пороги та безпечний експорт. Набір містить 200 детерміновано згенерованих фінансових прикладів.

## Обмеження

Немає конекторів, автоматичної зміни бюджетів, прогнозу LTV, причинного аналізу, статистичної оцінки невизначеності, окремої моделі повернень чи виявлення відсутніх у двох джерелах оголошень. Успішна перевірка файлів не доводить правильності бізнес-визначень та атрибуції. Для великого потоку подій потрібні попередня агрегація та інший механізм зберігання/обробки.
